# RFC SDK2：可信运行接续

创建：2026-09-18。任务：SDK2-01b／07／08。状态：**新API、独立可信发行者与受信serve原Store内部接线已实现，最终验收进行中；SDK公共配置和各原生消费尚未开放**。本文件与[缓存连续性 RFC](RFC-SDK2-缓存连续性.md)并列补足其可信血缘前置，不修改现有 SDK1、L0、原 TWP、七字段缓存交换信封、SessionStore 或缓存 schema。

## 1. 本轮结论与实码依据

平台能确认一个当前运行资源属于谁，但尚不能确认两个不同运行资源来自同一份合法历史。保持当前 API 对跨 runtime 的拒绝，不能用同一应用／末端用户、有效票据或客户端声明代替接续证明。缓存组只影响上游提示缓存，不能成为历史访问权限或另一份费用账本。

| 调查路径 | 当前事实 | 可使用的权威边界 |
|---|---|---|
| API `src/t1/routes.ts` 的 `/t1/heartbeat` | 合法 app_user 可免费登记符合既有格式的新平台 sessionId；已存在资源核 owner、app、endUserId；没有模型费用 | 新运行本身的当前归属，不证明它来自哪个旧运行 |
| API `src/sdk2/cache/control-authority.ts` | C1 要求当前已登记且未归档的 SessionRow，并实时核认证、应用和用户 | 当前运行授权；不发行跨运行证明 |
| API `src/store/types.ts` 的 SessionRow／原 MySQL 会话方法 | 保存公开／内部 ID、主体、应用、末端用户、时间、归档及 meta；没有持久的原 Store 来源、恢复代际或运行接续记录 | 原会话归属事实；Store 层 JSON 不是签名见证。公开 heartbeat 的 meta 有白名单，伪 parent 字段实际返回 400 |
| SDK `packages/sdk/src/session.ts` 的 resume | 经旧 Store 恢复历史及存储的 platformSessionId；缺失时产生新号 | 本地恢复事实；API 目前不能认证这项本地事实 |
| serve `packages/server/src/v2/agent-session-factory.ts` | 原 Store 按实际 endUserId 和 sessionId 读取，恢复 platformSessionId | serve 进程内来源权威；目前没有向 API 委托这项权威的协议 |
| kernel `packages/kernel/src/archive/session-binding.ts` | 原 Store 身份、历史提交、代际及绑定由进程内能力约束 | 内核私有能力，不能直接序列化成终端凭据或网关授权 |

首次 C1 无需先发一笔收费 exchange。显式启用缓存的宿主必须先确认**当前准确 runtimeSessionId** 的真实免费 heartbeat 成功，再协商并打开 C1。SDK 的普通 bundle／features 共享缓存不能证明该运行已经登记：其缓存键不含运行号；原容错 heartbeat 也可能吞掉失败。新消费链独立执行严格前置，默认 SDK1 路径仍保持原行为和原 I/O。

原 heartbeat／renew 的 `410 session_archived` 表示显式归档终态。30 天闲置仅影响活跃列表，并不等同于写入 archived_at；原 MySQL touch 也不清除 archived_at。因此不能把当前 410 当作普通租约过期，再自动继承旧缓存组。旧 SDK 的换号兼容行为不变；新缓存链对旧票据跨号保持拒绝。

## 2. 必须分开的身份

1. **运行身份**：当前 API SessionRow、运行号及其主体归属。换号必须真实登记新资源。
2. **历史来源身份**：原 Store／已验证档案及被接受的历史代际、删除代际、恢复提交。不能由客户端自己填写后即获得权威。
3. **逻辑缓存关系**：scope、logicalRef、绑定、组代际及当前政策。票据只能索引已存在的关系。
4. **业务请求身份**：原 TWP requestId、完整交换帧及原 owner 财务键。接续不改写、不迁移、不重放这把费用身份。

同 app／endUserId 只满足范围隔离。两个独立新会话仍应有独立逻辑组；同一用户上传相同文本，也不自动形成恢复关系。

## 3. 新协议所需的可信来源

拟新增独立的**宿主运行接续协议**，先会签认证、持久化和错误合同，再冻结具名 API／schema。本文不确定路由名，也不借原 TWP meta、heartbeat meta、缓存 exchange metadata 或现有 resume intent 偷增字段。

可被平台接受的宿主需要独立注册并限定权能：issuer 与应用、可证明的原历史来源、允许的恢复操作和有效期绑定。不能仅凭普通 app_user、长期 appkey 或持票就认为宿主已核对历史；具体采用何种宿主认证、密钥托管和撤销方式，仍须与 USDK 身份合同会签。纯终端没有该能力时继续拒绝跨运行继承，不能把密钥下发到客户端解决。

宿主只有在原 Store／档案**实际完成恢复并接受当前历史**后，才可申请接续。见证至少绑定：当前授权主体与应用／用户、issuer、原来源身份和提交代际、删除及授权代际、旧／新 runtime、原 logicalRef／绑定／组代际、期望修订、新运行登记事实、单次接续 ID、用途和截止时间。字段名称、编码、最大长度、加密范围及物理计量在新 schema 冻结时确定；不在本批提前写库。

平台必须能核对 issuer 当前仍有这一来源的见证权，并将见证与现有映射的来源关系关联。若平台无法验证来源、删除状态或受信宿主声明，不发行接续权。平台配置摘要、缓存投影摘要、票据存在及同主体均不能补足缺失的历史权威。

## 4. 拟议状态机与事务边界

接续分为原意图登记／查询和消费。登记不是允许执行模型，消费也不能触发 provider。宿主在出网前耐久保存原控制意图及幂等 ID；未知提交只查询／重放该意图，禁止重新铸造 ID 假装第一次操作。

平台沿原 owner 锁序，在同一事务核当前授权、issuer／来源／删除代际、原映射与绑定状态、新运行归属、期望修订及接续未消费；原子记录接续事实、消费一次性授权并更新相应绑定／票据。以唯一约束、代际和 CAS 防止多实例同时接管、旧见证回滚或 ABA。行锁、原资金域及缓存库存锁序须与 C1／C2 会签，不另起嵌套事务冒称原子。

当前显式归档／删除的旧资源不能凭这项提案复活。若未来要支持非删除性质的运行失效换号，必须先有**平台可验证且区别于显式删除**的结束原因，以及历史来源仍可恢复的授权证据。当前数据模型没有这项事实，不能从 410 或客户端描述推断。

接续只影响后续合法的新请求如何选择缓存组。旧 C2 已受理、结果未知或已完成记录仍按原运行、完整原帧和原财务键查询；不得把其 frame 改成新 runtime，也不得借接续新建 requestId 重发模型。账务已结算不是响应正文可重建的证明。

## 5. 恢复、撤销、保留与兼容

宿主重启后须从实际耐久记录恢复原控制意图、已确认接续回执和未决 C2 阻断。仅进程内 Map 不足以宣告跨重启安全；未知状态下不自动降级旧 exchange、切模、换键或新建冷会话继续执行。

显式冷新建仍可作为独立选择：重新核当前历史使用权及模型准入，建立新逻辑关系，不声称续接旧组。不把恢复失败偷偷转换为 `new`，不把缓存不可用转换为再次收费。

未来 GC 将接续行纳入原子库存，计入应用／用户／全局帽。未决接续、来源依赖和仍需拒绝旧请求的锚点不能按年龄删除。压缩保留完整身份和拒绝锚点；旧签名／加密 key 在实际引用清零前保留。迁移、回滚、满帽维护和多实例竞态均需真实 MySQL 验证。

默认 SDK1 不新增协商、存储字段、等待或网络请求；缺省仍走原路径。首批内部 SDK／serve 装配不等于 `/v3` 两跳 feature，API 的票据与宿主见证不得交给下游终端。公开新能力需要独立协商、契约出口、权限与原生消费验收。

## 6. 开发顺序与退出条件

| 阶段 | 实施内容 | 可交付判据 |
|---|---|---|
| 本批保护 | 免费 heartbeat 前置；同运行消费；跨运行拒绝反例；禁止新链自动换键／降级 | 真实原 HTTP 与真实 C1 数据库测试；默认旧链兼容；不声称跨重启耐久 |
| 协议会签 | 宿主 issuer／来源见证／删除及代际、原意图耐久、新 API 和错误合同 | SDK2-01b 与 USDK 身份边界签认；具名 schema 和兼容金样冻结 |
| 持久实现 | 接续表与计量、原锁序、消费 CAS、只读原键查询、迁移及回滚 | 双 Pool 竞争、未知提交、撤权、GC 和断网重启实证 |
| 宿主接线 | SDK 原 Store／serve 真实恢复提交后签发见证；重启恢复未决阻断 | 真实 Store 而非自报 parent；两次进程生命周期；不二次出网／计费 |
| 对外开放 | 新 feature／SDK 配置和双语示例，各原生端消费 | 冻结 SDK1 全矩阵及各宿主真实链通过，再开放新特性 |

本批可安全完成首次登记和同运行消费，**不能在现有权威下安全接完跨运行继承**。阻断是缺少可认证的恢复来源、删除语义和耐久接续合同，不是缺一个允许同用户换号的条件分支。

## 7. 对抗式验收单

- [ ] 同 app／用户但独立新 runtime，持旧票或自报 parent、来源已验证、代际，均不得接旧组。
- [ ] 跨 app／用户／owner，伪 issuer、撤销 issuer、超权来源及错误 audience，在出网前拒绝。
- [ ] 显式归档／删除、旧来源代际、旧映射修订、旧组代际及失效见证不可恢复。
- [ ] 同 ID 异义拒绝；同意图双实例消费只有一次；未知 COMMIT 只查原键，不能签发第二条关系。
- [ ] 实际恢复失败、ACK 丢失、宿主退出及重启，不凭本地“成功”标志补发授权。
- [ ] 旧 C2 pending／unknown 不因接续、续票、切模或 fallback 再执行；原 frame 字节与财务键保持。
- [ ] GC 不删未决／被引用见证，满帽仍能做有界回收；坏行、缺钥和超界依赖保持拒绝并可定位。
- [ ] 默认 SDK1 零新增 I/O；内部装配不开放终端两跳 feature；旧版严格解析与原 Store 恢复不退化。

本批已落的拒绝测试位于 API `test/sdk2/cache-runtime-lineage.test.ts`；实际通过数与未跑边界以 `archive/20260918-SDK2-cache-next/lineage/` 回执为准，本文不把提案清单当作已验结果。


## 8. 本批实施增补

前文调查与阻断是前批时点；本批在独立 `sdk2-runtime-continuity-v1` 落下可信issuer认证、来源／历史／删除代际和同事务新binding接续。实码、原始证据与仍未完成的宿主链见[执行记录](../report/SDK2-07-宿主持久恢复与两跳接续-2026-09-18.md)。不修改旧C1/C2合同，不凭同用户放行。SDK／serve的真实Store自动签发、原删除协调与接纳新binding尚未接合；本RFC的最终跨端验收清单仍开放。

## 9. 可信宿主内部消费增补

2026-09-18后继批将原Store确认见证接入独立协议，见[可信宿主来源链执行记录](../report/SDK2-07-可信宿主来源链与有界依赖回收-2026-09-18.md)。来源稳定身份与历史代际保存在独立宿主vault，原intent先落盘再签名；运行恢复策略由受信宿主配置，终端不自报issuer或跨运行证明。

目标客户端独立耐久接纳与宿主别名发布有显式未知恢复，原runtime/业务frame/财务锚不搬迁。API接续确认后，再通过原Store方法对账platformSessionId；同目标待Store ack标记保留到真实写入确认。实际历史在未知期间变化时，先确认原接续，再保持同目标guard完成当前史checkpoint，不能静默换新运行继续。

FileStore私有删除守卫将原手删/retention的墓碑确认前置；缺卷、坏尾、当前驱动尚未真实收尾、创建竞态、未知确认都必须保留原史；粗态ended不授予删除、替换或容量逐出许可。默认SDK1没有这项配置和IO。新运行接续不绕过API显式归档终态；原生介质、新公有配置、生产全实例覆盖以及付费provider命中仍独立待验。

## 10. 终结额度与内部退休增补

本批[终结与退役记录](../report/SDK2-07-终结额度与运行安全退役-2026-09-18.md)把来源delete需要的完整操作库存改为enroll时独占预留；普通接续不得挤占，delete在原同事务转换真实库存，不放宽总帽或资金规则。旧来源的受控回补失败不得伪称已保障，既有删除仍可按原帽尝试。API101保留终结保障代际，不能用旧实现忽略新预留。

只有已验证resume/delete回执或客户端已耐久确认close可以授权整runtime退休。providers用单一永久退休meta归并原完成锚；未决/未知/活动帧不能退休。宿主确认原Store新运行号后才释放原目录活动槽。跨库任一步失败继续原意图、原目标和原证明，不重新生成身份。

显式SDK2新两跳链的已退休旧操作保留规范原请求摘要：异义同键仍冲突，同义回执返回原协议已有receipt_expired/410，retryAction=none，fallback=none。不向冻结错误schema加入内部runtime_retired；不修改SDK1默认、旧根出口或原Store接口。退休不是会话原文授权、账务迁移、自动冷fallback或重新接纳旧receipt的权限。

每批维护只有一次vault快照，最多8个冷运行库打开、8笔目录提交；异步期间revision变化停止旧计划，游标防候选饥饿。每运行永久墓碑和原请求摘要仍计量，物理SQLite不删除/不VACUUM，不能宣称无限容量。旧纯C1库缺terminalProof时不自动退休，另列受信迁移边界。


## 11. 本地终结空间与在途收尾

本批见[进度与实施记录](../report/SDK2-进度复核与本地终结空间-2026-09-18.md)。serve私有vault以真实填充行预留Source/C1操作/未来别名与票据/runtime目录的峰值；API已预留不代替本地保障。C1及可信resume先同事务固定意图与未来槽再出网，COMMIT未知仍保原键；冷恢复复核占位，不补造新身份。source/binding活跃行及pending操作固定64KiB、runtime固定8KiB、session/ticket占位512字节，key和AES-GCM开销另按原Store计量。退休目录不依赖其它事务刚释放的字节，完全相同对账不重复FULL写。

旧未保障来源补额不足可继续尝试原delete峰值，但不得标记已有承诺；已承诺记录损坏不降为legacy。两跳及continuity宿主metadata升级v2，旧writer拒绝，原v1受控前向升级；不支持忽略新预留的旧writer回退。首次C1未决而尚无正式source也必须挡住原史删除。逻辑帽、页帽及SDK1协议不改；填充只保障逻辑额度，不保证物理disk/journal空间和掉电。

删除专用加载仅接纳既有ready catalog和原SQLite库，不新建运行或扩充旧catalog；普通加载即使命中缓存仍须补预留。已验真退休且来源/绑定栅栏全部满足后，旧未预留目录可维持原紧凑永久墓碑并同事务减少活动计数，新预留目录仍消费自己的固定预算。此分支不授权旧缺proof运行退休。
